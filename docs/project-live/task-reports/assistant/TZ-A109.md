## Scope and root causes

The stale selected-field focus was applied too broadly. Generic plural questions were not represented as a separate company-wide scope, `Какие это поля?` was absent from the deterministic field-directory classifier, and operation argument normalization reused `selectedFieldId` whenever the current message had no explicit field. The parser also recognized `Поле 15` but not the postpositive form `15 полю`.

The DATA loop trusted a non-empty model response even when a generic field list contradicted the preceding company-wide count. Empty DATA responses ended in a technical fallback string. Product matching supported substring, transliteration, and one edit, but `курмаина` needs a safe two-edit fuzzy comparison against the unambiguous Curamin identity.

## Implementation

- Added a Unicode-safe scope classifier for company-wide field, operation, and warehouse questions.
- `Какие это поля?`, `Покажи все поля`, and `Какие поля есть?` always clear a stale single-field focus and call `search_fields` without a field filter.
- General plural operation questions call `get_active_operations_summary` without the selected field. Field focus is retained only for explicit follow-ups such as `А культура?`, `А площадь?`, and `А какие там операции?`.
- Added postpositive field-number parsing for `Что по 15 полю?`; this request no longer falls through to product lookup.
- Added one fail-safe repeat of the correct read-only ERP tool when the DATA response is empty or the generic field count contradicts the preceding count. If the model still produces no answer, supported tool outputs are rendered deterministically rather than exposing a technical phrase.
- Added conservative Damerau-Levenshtein product matching with transliteration normalization. `курмаина`, `курамин`, `фолиар`, and `Curamin` resolve to the single Curamin Foliar identity. Existing praise exclusions, including `Маладээс`, remain outside ERP lookup.
- Added mocked and REAL A109 harnesses plus a fail-closed local runtime launcher. No Core file, migration, QA dataset row, ERP row, or production resource was changed.

## Owner finding: Field15 planned status

DATE: `2026-07-19`

Owner acceptance found one remaining contradiction: `Что по 15 полю?` described the Field15 operation as active, while the company-wide `Какие операции идут сейчас?` correctly excluded Field15. Ground truth is `status=planned`.

ROOT CAUSE: `get_field_card` counted every non-completed/non-cancelled operation as `active_operations_count`, so `planned` was exposed to the model as active. The runtime bundle also had to be rebuilt after the source patch because the safe owner launcher serves `.next`.

FIX:

- `planned -> запланирована`, `in_progress/active -> выполняется сейчас`, `completed/verified -> завершена`.
- `get_field_card.active_operations_count` now uses the same `isActiveOperationRow` logic as the company-wide active operations list.
- `get_field_card` exposes separate `planned_operations_count`, `active_operations_count`, and `completed_operations_count`.
- Compact tool rows include an operation status/count summary so the model sees strict wording.
- A fail-closed answer post-processor replaces a contradictory Field-card answer with grounded tool fallback when `planned>0` and `active=0`.
- The A109 safe runtime launcher now removes the stale `.next` junction before deleting `.a109-runtime-owner`, avoiding Windows junction lock failures.
