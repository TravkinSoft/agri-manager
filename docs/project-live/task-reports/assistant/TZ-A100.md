## 2. Executive verdict

The main defect is not that OpenAI is weak. The system persists and reloads chat history, and the UI even sends up to 20 recent messages, but the engine never includes `input.chatHistory` in any OpenAI request. OpenAI sees the current message, system instructions, runtime context, and a compact client state—not the conversation shown in the chat.

The current runtime is a hybrid:

1. a fast OpenAI classifier chooses `CHAT`, `QUESTION`, `DATA`, or `ACTION`;
2. some `DATA` classifications execute a hardcoded direct tool before the main planner;
3. most remaining data questions enter a heavy model planner with function schemas;
4. if that planner fails, a large deterministic regex router and hardcoded tool map take over;
5. local UI fast paths can edit a draft without calling the server engine at all.

This produces the impression of a model that is much less capable than the connected models: the model has no transcript, tool choice can be constrained or replaced by code, field parameters are lost by regex normalization, and many settings displayed in the UI are not enforced on the primary planner.

Two blocking security findings were found:

- the legacy operation-draft confirmation route allows every assistant role to perform an operation write through service-role access, bypassing the canonical operation-create role list and season guard;
- Knowledge Base DELETE archives a document by caller-supplied `documentId` without `company_id` ownership filtering while using the service role.

The legacy runtime must remain unapproved for Travkin Assistant V1.

## 4. OpenAI call audit

### API and models

Text generation uses `POST https://api.openai.com/v1/chat/completions`. The Responses API is not used. There is no OpenAI conversation ID, `previous_response_id`, or server-managed conversation state.

Code-level routing is:

| Call | Code default | Selection behavior |
| --- | --- | --- |
| GPT decision/classifier | `OPENAI_ASSISTANT_FAST_MODEL` or `gpt-5.4-mini` | Forced fast tier, temperature `0`, `max_completion_tokens: 320`. |
| General/knowledge answer | fast tier, normally `gpt-5.4-mini` | Forced fast tier; current user message only. |
| Primary tool planner | `OPENAI_ASSISTANT_HEAVY_MODEL` or `gpt-5.5` | Forced heavy tier; up to three Chat Completions turns per candidate model. |
| Voice transcription | `gpt-4o-mini-transcribe` | `/v1/audio/transcriptions`, not part of text history. |

The UI offers `gpt-5.4-mini` and `gpt-5.5`, and settings default to `OPENAI_ASSISTANT_MODEL || gpt-5.4-mini`. That selected model is not authoritative: classifier/general paths force fast and the primary planner forces heavy. Exact deployed env overrides were not read, and no live OpenAI request was made, so the exact production model instance remains unverified.

### Parameters and instructions

- Requests contain `model`, `messages`, optional tools with `tool_choice: auto`, optional `temperature`, and optional `max_completion_tokens`.
- `temperature` is omitted for model names starting with `gpt-5.5`; the classifier hardcodes zero.
- Main general/planner calls do not set an output-token limit; only the classifier and settings validation ping have small limits.
- `reasoningEffort` is saved and shown in UI but is never sent to OpenAI. Runtime reports `reasoningApplied: false`.
- There is no OpenAI `developer` role. Instructions are sent as one or more `system` messages.
- The base prompt is code-owned `travkin-core-v1`. Environment override wins DB override, but both are appended after the core prompt rather than replacing it. Company instructions and KB/memory text are also appended.
- The prompt says to answer in Russian even when runtime locale can be `kz` or `en`, creating a language conflict.

### History and tool protocol

The UI builds up to 20 messages plus a synthetic working-context system message. The API filters this array and places it in `AssistantEngineInput.chatHistory`. No subsequent function reads that field. The classifier, general answer, and model planner construct new message arrays from system prompt, context/state text, and the current user message only.

Planner tool calls and tool results exist inside one planner request loop, so the model can see results during that single request. Across user turns, tool calls/results are not replayed to OpenAI. They are stored only as metadata on the assistant message, not as durable `tool` role history.

### Error behavior

There is no request timeout or `AbortController`, no general retry/backoff, and no rate-limit-specific recovery. Candidate fallback is mainly for an unavailable model. The planner can try alternate candidate models, then fall back to deterministic legacy routing. General-answer failure returns degraded safe text. The normal API returns HTTP 500 for unhandled failures. No streaming partial answer is available while any of these calls wait.

The exact reason `Покажи поле 28` followed by `А материалы?` is not one conversation is:

1. the first answer can set `focusEntityType=field` and a field ID/label in returned `sessionState`;
2. the UI sends that state on the next request and also sends the transcript;
3. the transcript is discarded by the model pipeline;
4. only the compact focus state can connect `материалы` to field 28;
5. if focus was not produced, was overwritten, expired in local storage, or leaked from another thread, the second message has no linguistic antecedent and becomes a generic question or wrong tool call.

Thread switching makes this worse: messages are thread-specific, but main-panel `sessionState` is not. A follow-up can therefore lose the current thread's entity or inherit another thread's entity.

## 6. Router, regex, and fast paths

The phrase “logic before GPT” is only partly true for the current default path. `runAssistantEngine` first calls a fast GPT decision layer. However, important deterministic paths still exist before the main reasoning model and can bypass it:

| Rule/path | Trigger | Can intercept conversation? | Tool without main planner? | Decision |
| --- | --- | --- | --- | --- |
| Client draft-edit parser | A message matches a local edit command and a draft card exists | Yes | No server/OpenAI; edits local draft | Rewrite into explicit draft state machine; do not infer from arbitrary chat text. |
| Fast GPT classifier | Every normal request | Yes | Can emit a `tool_hint` used directly | Keep concept, but include transcript and constrain output with validated typed schema. |
| Direct DATA fast tool | Classifier says DATA with recognized hint | Yes | Yes | Keep only for narrow, typed, policy-checked read tools. |
| GPT planner | Most remaining data/action requests | Yes | Chooses among 41 schemas | Keep only after central allowed-tool/role/side-effect enforcement. |
| Regex fallback router | Planner/model failure or legacy branch | Yes | Yes, via hardcoded mapping | Reduce drastically; retain only deterministic safety and explicit navigation/draft grammar. |
| Current-page bias | Short/ambiguous warehouse, field, weighbridge, crop questions | Yes | Often | Keep as weak context, never as a replacement for explicit user text/history. |
| Typo/product prompt rules | Classifier prompt explicitly treats `привент`, `превет`, `селетра` | Yes | Can prevent/trigger inventory search | Move typo normalization after GPT intent extraction or use confidence thresholds. |
| Navigation policy | Explicit markers such as “открой/перейди” | Yes | Produces client action | Keep strict explicit gate; do not auto-navigate informational questions. |
| Answer regex state inference | Client re-parses assistant answer to infer entity state | Yes | No | Remove; state must come from structured tool/model output. |

`engine/router.ts` remains a large keyword/regex classifier. Its exported `classifyAssistantIntent` ignores settings and returns only `fallbackIntent`. The default engine mode is `model_first` and planner-first defaults on, but regex behavior still becomes production behavior on failures and in hardcoded branches.

Static pure-router traces confirmed:

- `Привет`, `привент`, and `Что такое фертигация?` become `general_question` in fallback;
- `Покажи поле 28` becomes `fields_overview` with `field: "28"`;
- `А материалы?` without focus becomes `general_question`;
- `Дай все поля с названием Сад` becomes `fields_overview` with `field: null`;
- `Найди поле площадью 22 га` becomes `fields_overview` with `field: "22"`;
- `Сколько осталось селитры?` becomes `general_question` in fallback;
- `Создай операцию` becomes `create_draft`.

This proves that model outage/degradation changes semantics substantially rather than only reducing answer quality.

## 7. Tool inventory and policy

There are 62 runtime tool definitions in `toolRegistry` and 41 model-facing function schemas. Planner schema names are aliases and map to runtime tools/intents. The primary planner receives all 41 schemas; it does not filter them through `settings.allowedTools`. The legacy deterministic selector filters some candidates but force-adds `requiredTools`, so even that setting is not absolute.

### Common runtime contract

Unless a row says otherwise, tools receive server-derived actor, `companyId`, settings, normalized runtime context, session state, and typed intent. They return a title, rows, source metadata, optional summary/actions, and state hints. The query route admits ten assistant roles, but runtime tools do not have individual role policies. Most ERP reads explicitly filter `company_id`; season-sensitive tools use intent/runtime/default season (usually 2026), while entity/warehouse/current-context tools may be season-neutral. Tool exceptions are caught and can produce tool errors, alternate model/tool attempts, deterministic fallback, or a no-data response.

Because all calls use the service client, RLS is bypassed. Company isolation therefore depends on `resolveCompanyForActor` and every explicit query filter; there is no central proof that every future tool preserves it.

### Field-search root cause

`Дай все поля с названием Сад` is classified as `fields_overview` but the fallback router stores only the full `query` and `field: null`. It does not extract a typed name. Tool selection then treats list language as a generic list, `search_fields` sets `effectiveQuery` to null, and `get_fields` applies text filtering only for `filtered_summary` or when the output-list query contains a 1–3 digit number. The same branch force-adds `get_field_land_bank_summary` when no field query exists. The result can therefore be all fields or general land-bank statistics instead of matching names.

`Найди поле площадью 22 га` has no typed `area_ha` parameter/schema. Generic numeric extraction turns `22` into a field code. Any later text filter is substring matching across row values, not numeric area comparison. The query can incorrectly look for field number 22 or rows containing “22”.

## 8. Knowledge Base audit

### Storage and ingestion

Tracked schema defines `knowledge_bases`, `knowledge_documents`, and `knowledge_document_chunks`. RLS is enabled in migrations, but assistant runtime uses service-role access and therefore relies on explicit company filters.

Supported uploads are PDF, DOCX, TXT, and XLSX, maximum 25 MB. Extracted text is capped at 500,000 characters. Paragraph chunks are at most 1,800 characters with 180-character overlap. Up to eight chunks are used, with snippets capped at 700 characters and total company context capped at 2,600 characters.

No embedding generation, vector column, pgvector search, semantic vector RPC, or reranker was found. “Semantic memory” is a checked-in Markdown knowledge file plus keyword expansions/scoring. Company KB retrieval tokenizes at most seven terms, uses PostgREST `ilike` over chunk content/filename/extracted text, scores substring matches, and returns the best chunks.

### Runtime use

KB is used for general/knowledge questions when `internalLibraryFirst` is enabled. Static knowledge and company KB are loaded in parallel, then embedded into a system prompt. Live ERP data paths normally do not mix KB context with tool facts. The final response exposes only a generic library source hint, not structured document/chunk citations or per-claim provenance.

### KB risks

1. `DELETE /api/assistant/knowledge` accepts only `documentId`, uses the service client, and updates `knowledge_documents` and chunks by ID without a `company_id`, knowledge-base, or owner predicate. A company admin able to obtain another document UUID can archive another tenant's content.
2. `GET /api/assistant/knowledge` calls `getOrCreateGlobalKnowledgeBase`; a nominal GET can insert a row. This is a hidden write side effect and contract-incompatible.
3. Uploaded document text, company instructions, and user memory are appended to system-level prompt content. There is no robust untrusted-content boundary, instruction stripping, or citation-grounded answer validation, so prompt injection from a document can influence model/tool behavior.
4. The runtime's explicit company filters are generally present in retrieval, but service-role usage means RLS is not a defense-in-depth layer.

The separate `knowledge_intake_*` product-metadata workflow is not the chatbot KB and should not be counted as runtime RAG.

## 10. Latency and observability

### Main latency sources

- Initial request performs company, settings, and memory reads in parallel.
- Every normal message performs a classifier OpenAI call. A knowledge question then performs KB reads and a second OpenAI call. A general data question can perform classifier + up to three planner OpenAI turns + sequential tool calls.
- Planner tool calls are awaited sequentially inside a loop.
- After the answer, user-message insert, assistant-message insert, thread updates, optional title update, and audit insert add DB round trips before JSON is returned.
- No assistant answer streaming exists; the user waits for the full chain.
- No timeout, retry/backoff, settings cache, tool-result cache, or explicit prompt-cache instrumentation was found.
- The prompt is large and highly dynamic. A stable prefix exists, but prompt caching is neither configured nor measured.

### Observability

The engine collects classifier/planner/tool/model/validator/render/total times and prompt/completion/total tokens. Debug UI can display them. Tool calls record duration. Cost is not calculated or stored. Console errors exist for several failure paths.

`writeAssistantAuditLog` writes request/response excerpts, runtime context, and compact tool data to `assistant_audit_logs`, but no tracked migration for that table was found. Missing-table/schema-cache errors are silently ignored, so audit logging can appear enabled while persisting nothing. Conversely, if the table exists out-of-band, the `storePromptSnippets` and `storeToolPayloads` privacy toggles are not honored.

No response feedback loop or evaluation result store was found. Existing QA/trace scripts require Supabase/OpenAI and write report artifacts; they were inspected but not executed because A100 prohibited real DB/API use and allowed only three changed files.

## 14. Proposed first safe scope for TZ-A101

TZ-A101 must not start under contract 0.1 without owner approval and a core compatibility decision. The first safe implementation slice should contain no DB/schema/migration change and no production write capability:

1. Create one read-only assistant policy boundary that receives the authenticated actor and server-selected company, then enforces role, tool allowlist, company, season, row limits, and `side_effect=none` before any tool runs.
2. Expose only a small initial tool set: current context, field card/search/land-bank summary, warehouse stock, crop-structure summary, and active-operation summary. No drafts, confirmations, KB administration, navigation execution, raw generic resolver, or write endpoint.
3. Build one bounded conversation payload from the active thread: validated user/assistant turns, explicit structured focus state, and current route context. Actually pass it to OpenAI. Do not rely on assistant-prose regex.
4. Make focus/pending state thread-scoped in memory for the request. For A101, avoid a new DB table; derive from structured recent tool metadata or keep it in a signed/validated request state until a separate storage contract is approved.
5. Add typed field parameters (`name`, `number`, `area_ha`, tolerance, season) and deterministic tests for `Сад`, `22 га`, `поле 28`, and the materials follow-up.
6. Make effective model/tier and effective settings explicit in diagnostics. Remove or hide any control not enforced in this slice.
7. Add unit/static integration tests with mocked OpenAI and mocked Supabase. Include cross-company denial, role denial, tool allowlist denial, no-side-effect proof, history inclusion, and no navigation/write action.

Acceptance boundary: no service credentials exposed, no direct SQL, no production calls, no write route reachable, no DB changes, and no claim that legacy `/api/assistant/**` is approved merely because it exists.
