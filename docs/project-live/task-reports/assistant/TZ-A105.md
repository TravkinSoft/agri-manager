## Implementation result

Long conversations now keep the newest 19 prior meaningful user/assistant messages and append the current message. The older part is summarized into a versioned server-owned object containing topics, selected objects, decisions, confirmed facts, unresolved questions, rejected/cancelled alternatives, last safe action and update time. Secret-like, system, tool, debug, injection and technical rows are excluded. The summary is stored in assistant message metadata and restored after reload; the client cannot supply it.

Unresolved clarification has its own versioned metadata object. It is bound to `threadId`, records expected clarification and related entity IDs, and transitions through `open`, `resolved` or `cancelled`. A different thread discards the state.

The existing memory table is not sufficient for a production confirmed-memory contract. The local prototype therefore uses explicit candidate types and server-owned scope, but its route is disabled unless `ASSISTANT_MEMORY_V1_ENABLED=1` in a non-production process; production forces it off. Explicit memory commands create `candidate`, never `approved`. Approval/rejection requires a separate confirmed API action. Retrieval excludes candidate, rejected, expired and foreign rows and returns no more than five relevant approved preferences. Delete is current-user/current-company only and requires explicit confirmation before an audit event.

The prototype permits only language, brevity, explanation level, preferred format, confirmed role, source preference and durable work rules. It rejects secrets, temporary inventory/operation facts, unconfirmed claims and attempts to override security policy. Company-wide memory is not represented by the V1 public type or route.
