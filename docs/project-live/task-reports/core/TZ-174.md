## Root cause

The TZ-172 CSV and SQL files were valid BOM-less UTF-8. The corrupt Russian
safener labels were introduced when Windows PowerShell 5.1 read SQL with
`Get-Content -Raw` and no explicit `-Encoding UTF8`. The legacy ANSI code page
decoded the UTF-8 bytes before the SQL text was serialized to the database
tool. PostgreSQL was not the corruption source.

The failure was reproduced with the exact Cloquintocet-mexyl Russian literal:
the default PowerShell read returned a legacy-code-page sequence, while
`Get-Content -Encoding UTF8` returned `Клоквинтоцет-мексил`.

## UTF-8-safe package

The external package is stored outside Git at:

`C:/Users/TRAVKIN/Downloads/CodecSaaS/audit-output/TZ-174/apply-package/`

It contains canonical JSON, four UTF-8 CSV files, apply/rollback previews,
encoding evidence, owner review and a SHA-256 manifest. All human-readable
artifacts decode as strict UTF-8 and are normalized to NFC. A total of `4012`
package text values were checked; mojibake values and NFC failures are both
`0`.

Executable SQL is ASCII-only and represents every non-ASCII string with
PostgreSQL `U&` Unicode escape literals. This removes dependency on a caller's
Windows ANSI code page. Both scripts fail closed unless `client_encoding` is
`UTF8`, retain explicit owner tokens, use exact UUIDs, and contain no broad
catalog or product updates. Rollback suppresses timestamp triggers inside its
transaction so the original `updated_at` values can be restored exactly.
