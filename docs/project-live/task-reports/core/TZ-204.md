## Result

The P0 operation lifecycle now crosses the API/DB boundary through one PostgreSQL
transaction per mutation. Create, material replacement, accept/start, progress,
request preparation, specialist receipt, warehouse issue, return/reconciliation,
complete and controlled request creation use authenticated, company-scoped RPCs.

The API no longer reports success after a partial sequence of browser/server writes.
Every mutation waits for the full RPC commit. Errors are returned as clear conflict,
validation, permission or not-found responses.

## Atomic contracts

- Create writes operation, execution lines, material rows, request and request items
  together. A material operation cannot succeed without lines/request.
- Material edit locks the operation and request, rejects issued/started work and
  replaces the complete material/request-item set in one transaction.
- Progress locks the operation/line, checks area, inserts the shift fact and updates
  aggregate/task status plus audit log together.
- Issue locks request/items and the canonical stock identity, checks live balance,
  writes OUT ledger and synchronizes request/material state together.
- Return separates consumed, returned and loss. Warehouse acceptance writes IN and
  closes reconciliation only when `issued = consumed + returned + loss`.
- Complete requires full area, reconciled warehouse facts and finalized linked
  weighbridge tickets, then writes final statuses and field history together.

## Idempotency and concurrency

`operation_mutation_receipts` stores the response for a unique company/action/key
and rejects key reuse with another request fingerprint. Transaction advisory locks
serialize retries. Business rows use `FOR UPDATE`; stock identities use ordered
advisory transaction locks.

Verified with real QA JWT:

- double create with one key: one operation;
- double issue/progress/complete retries: no duplicate mutation;
- two issue requests with different keys: one OUT ledger, second response
  `already_issued`, stock restored by the normal return flow;
- concurrent material edit and activation: final operation accepted, two material
  rows and exactly two matching request items;
- insufficient stock: HTTP 409, issued quantity stays zero.

## Existing QA integrity

operations had material rows but no warehouse request:

- `17600000-0000-4000-8300-000000000001` (`fertilizer_application`);
- `17600000-0000-4000-8300-000000000002` (`spraying`).

historical intent, then use the guarded request RPC with deterministic keys. TZ-204
