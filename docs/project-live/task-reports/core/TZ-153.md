## Approved memory model

1. Conversation summary: versioned record in `chat_messages.metadata`, bound to one chat/user/company and covered message range.
2. Unresolved question: versioned metadata with question, expected clarification, bounded object IDs, timestamps and `open/resolved/cancelled` state.
3. Memory candidate: existing `assistant_memories` row with authenticated provenance and `status=candidate`.
4. Approved/rejected memory: explicit `candidate -> approved|rejected` transition by the owner. The model cannot create approved memory.
5. Expiry: approved retrieval excludes `expires_at <= now()`.
6. Deletion: owner-only physical deletion after explicit confirmation; a content-free event remains in `assistant_memory_events`.
7. Company-wide memory: disabled. `scope=user` is mandatory for all V1 lifecycle rows.

Approved types are `language`, `response_brevity`, `explanation_level`, `preferred_format`, `confirmed_role`, `source_preference` and `durable_work_rule`. Secrets, credentials, temporary inventory/operation state, unconfirmed claims, foreign tenant data and security overrides are forbidden.

## RLS and runtime decision

The primary memory runtime must use a request-scoped authenticated Supabase client. `service_role` is not approved as the primary runtime. Server/Auth derives user, company, scope and actor; request-body IDs are not trusted.

The preview designs:

- owner/current-company SELECT;
- candidate-only INSERT;
- immutable candidate content and only `candidate -> approved|rejected` UPDATE;
- owner/current-company DELETE;
- owner-only SELECT on audit events, with no client event mutation policy;
- restrictive user+company policies for existing `chats` and `chat_messages` to neutralize legacy public-true policies without dropping data;
- indexes on RLS/retrieval and event lookup fields;
- Auth-derived lifecycle and content-free audit triggers;
- denial tests for anon, second user, second company, spoofed IDs, foreign approval and foreign delete.

The design follows current Supabase RLS guidance: exposed tables have RLS, policies use `TO authenticated`, `auth.uid()` ownership, both `USING` and `WITH CHECK` for updates, and indexed policy columns. A106 must verify all policies with real user JWTs.
