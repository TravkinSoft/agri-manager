## Root cause and encoding path

The original TZ-172 CSV and SQL bytes were valid BOM-less UTF-8. The corruption
occurred when Windows PowerShell 5.1 executed `Get-Content -Raw` without
`-Encoding UTF8`. Its legacy ANSI code page decoded the bytes before the SQL
string was sent to the database client. Node UTF-8 JSON/CSV serialization,
PostgreSQL storage and PostgreSQL `client_encoding=UTF8` were not the source.

The retained TZ-173 failed post-apply snapshot contains `64` mojibake text
values (`61` unique), including all six new safener Russian labels and affected
aliases. The canonical source selected for this rebuild contains zero mojibake.

The committed generator
`scripts/catalog/rebuild-component-utf8-package.mjs` now makes the transport
deterministic:

- strict fatal UTF-8 decoding and explicit rejection of BOM input;
- NFC normalization for JSON, CSV and review artifacts;
- executable apply/rollback SQL limited to ASCII bytes, with PostgreSQL `U&`
  Unicode literals for all non-ASCII values;
- fail-closed `client_encoding=UTF8` checks and task-specific apply tokens;
- SHA-256 manifest generation followed by an immediate independent recheck;
- package-wide mojibake detection before any isolated SQL execution.
