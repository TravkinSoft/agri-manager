## Root cause

The first isolated apply passed, but the second apply failed because named CHECK constraints were recreated unconditionally. The first visible failure was `products_density_contract_v2 already exists`; the same repeat risk existed for all ten named Warehouse Units V2 constraints.

## Fix

All ten named CHECK constraints now use one definition-aware guard:

1. create the constraint when it is absent;
2. leave it unchanged when PostgreSQL's normalized definition matches exactly;
3. raise an exception and stop when the same name has a different definition.

The comparison uses a temporary `LIKE` probe table and `pg_get_constraintdef(..., true)`, so it compares PostgreSQL-normalized definitions. It never silently drops or replaces a different live constraint. The approved TZ-144 constraint expressions were not changed.

The remaining migration objects were audited:

- 4 indexes use `CREATE INDEX IF NOT EXISTS`;
- 3 triggers use deterministic `DROP TRIGGER IF EXISTS` plus `CREATE TRIGGER` and do not duplicate;
- functions and views use `CREATE OR REPLACE`;
- columns use `ADD COLUMN IF NOT EXISTS`;
- grants and revokes are repeat-safe and show no privilege drift;
- no policy or helper type is created by this migration.
